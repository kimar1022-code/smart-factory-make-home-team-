# 9/9 실기 검증 체크리스트

순서에 이유가 있습니다. **위를 건너뛰면 아래가 무의미해집니다.**
각 항목은 `합격 기준`이 있고, 애매하면 통과시키지 말고 멈추는 쪽으로 적었습니다.

---

## 0. 전제 점검 (5분) — 건너뛰지 말 것

어제 저녁을 통째로 날린 원인이 여기 있었습니다. 벽을 만지기 전에 확인합니다.

```bash
curl -s http://127.0.0.1:8766/expo
```

- [ ] **`"wb": 4600.0`** — 5500 이면 어제 그 문제가 재발한 것. 파랑 점이 조각납니다.
- [ ] **`"bright"` 가 40 이상** — 오늘 아침 06:25 에 `0.14` 였습니다(거의 새까맘). 조명 켜졌는지 확인.
- [ ] 서비스 살아 있는지: `:8766 :8768 :8771 :8776 :8777` 전부 health 200
- [ ] **밑판 상태 확인** — 어제 다섯 벽 꽂힌 집을 포크로 출하지(-700,-100)로 옮겼습니다.
      조립대에 빈 밑판이 있어야 오늘 사이클을 돕니다.

> 합격 기준: WB 4600 · 밝기 40+ · 빈 밑판 배치 완료

## 1. 파랑·내벽 파지 서명 재촬영 ★1순위

**이걸 먼저 해야 아래 run4 검증이 깨끗합니다.** 안 하면 매 사이클 [▶계속]을 눌러야 해서
"하강 버튼만으로 도는가"를 검증할 수 없습니다.

| 색 | 현재 편차 | 서명 날짜 |
|---|---|---|
| blue | +1.07 / +1.70mm | 9/7 17:07 |
| red_in | +0.30 / +1.06mm | 9/7 20:21 |
| yellow / red / red_s | 0.3mm 이내 ✅ | 9/8 오후 |

절차 (색마다):

1. 해당 색 벽을 랙에 꽂아 둔다
2. 개별 사이클로 파지까지 진행 → 파지 게이트에서 멈춤
3. **그 상태(랙 위에서 문 상태)에서** `[좋은 파지 서명 저장]`
4. `[▶계속]` 으로 진행

- [ ] blue 서명 재촬영
- [ ] red_in 서명 재촬영

> 합격 기준: 다음 사이클에서 같은 색 파지 편차가 **0.3mm 이내**로 나오고 게이트에서 안 멈춤
> ⚠ 서명은 **랙 위에서 문 상태**에서만 유효합니다. 픽 자세(열림)나 z440 에서 찍으면 상수 편차가 박힙니다(9/7 실증).

## 2. 내벽 막힘 감시 재확인 → `JAM_FREE` 삭제 판단

지금 내벽은 **막힘 감시를 끈 채**(`descend_plain`) 내려갑니다. 그 결정은 **WB 5500 이던 때** 내린 것이라
근거가 무효일 수 있습니다. 내벽이 z+6 에서 서던 증상은 파랑이 z+11 에서 서던 증상과 같은 모양이었고,
파랑은 WB 를 고치니 사라졌습니다.

절차:

1. `tools/house_cycle.py` 의 `JAM_FREE = {"red_in"}` → `JAM_FREE = set()` 로 바꾸고 서버 재기동
2. 내벽 한 장 사이클 (외벽 4개 먼저 꽂은 상태에서)
3. 하강 로그에서 확인:
   - `(막힘 감시 노출 ... 채택 · 벽 점 N개 면적 A / 서명 S)` 에서 **A 가 S 의 60% 이상**
   - z+6 부근에서 멈추지 않고 **z340.5 까지 완주**

- [ ] 감시 켜고 내벽 하강 시도
- [ ] 통과 → `JAM_FREE` 삭제 확정, 다섯 벽 전부 감시 살아 있는 상태로 복귀
- [ ] 실패 → **되돌리고**(`JAM_FREE={"red_in"}`) 그 자리에서 멈춤. 게이트를 완화하지 말 것

> 합격 기준: 감시 켠 채로 z340.5 완주, 막힘 0
> ⚠ 실패하면 원인을 더 파기 전에 되돌려 놓습니다. 감시를 끈 채로 두는 것보다 낫지만,
> 막힌 벽을 계속 누르는 것보다는 멈추는 게 낫습니다(9/2 기둥 파손).

## 3. run4 실기 검증 ★서버 계약과 직결

**어제 고쳤지만 실제 run4 로는 한 번도 안 돌려봤습니다.**
(`return seated or auto_done` — 고친 뒤 돈 빨강·레드_S·내벽은 전부 개별 사이클이었습니다)

절차:

1. 외벽 4색을 랙에 꽂아 둔다
2. `[run4]` 실행 — blue → yellow → red → red_s
3. **하강 버튼만 4번** 누른다. 그 외 개입 없이 완주하는지 본다

- [ ] blue 통과 (1번 항목 했으면 파지 게이트에서 안 멈춰야)
- [ ] yellow 통과 — 안착 `unknown` 이어도 **중단 없이 다음으로 넘어가야** ← 이게 어제 고친 것
- [ ] red 통과
- [ ] red_s 통과
- [ ] `✅ run4 완료` 로그

> 합격 기준: **개입 = 하강 버튼 4번뿐**
> 실패하면 어디서 멈췄는지 로그를 그대로 남길 것 — 원인이 파지 게이트인지 안착 판정인지 구분이 중요합니다.

## 4. 출하 리프트 — 페이로드 등록 후 재현성

어제 1회 통과했지만 **페이로드가 벽 기준(0.7kg)인 채**였습니다. 알람은 안 났지만 정공법이 아닙니다.

- [ ] **집 + 포크 무게 실측** (몇 백 g 단위 어림이면 충분)
- [ ] FR5 페이로드 등록 (무게 + 무게중심)
- [ ] `tools/fork_carry.py` 로 운반 **2회 연속**
- [ ] 매 회 확인: 전 구간 도달 오차 ≤0.1mm, **운반 중 그리퍼 값 불변**

> 합격 기준: 2/2 성공, 그리퍼 값이 파지 직후 값에서 안 벌어짐
> 참고: 명령 47 을 줘도 죠는 50 에서 멈춥니다. 50 이 이 손잡이의 정상값이고, **거기서 커지면** 빠지는 중입니다.

## 5. `/cell/control` v0.3 실기 검증 — 🔴 조건부

**벽 작업이 전부 끝난 뒤에만 합니다.** 이유가 있습니다.

> 오케스트레이터를 `real` 모드로 띄우면 **FR5 를 두고 `bridge_server`(:8765)와 다툽니다.**
> 벽 꽂기가 그걸 쓰고 있어서 같이 띄우면 안 됩니다. 8/17 에 `cmd_server` 가 SDK 를 물고 있어
> 겪은 것과 같은 종류의 충돌입니다.

준비:

- [ ] `house_cycle`·`bridge_server` **완전 종료** 확인 (`:8765`, `:8776` 응답 없음)
- [ ] FR5 개통 순서 준수: `cmd_server → ActGripper → 정상종료 → real_robot`
- [ ] 오케스트레이터를 `exec_mode:=real` 로 기동

검증 항목 (sim 은 전부 통과, 실기는 처음):

- [ ] **V1** MOVE 구간 `immediate=true` → 1초 내 `cell_state=HELD`, `held_at=MID_MOTION`
- [ ] **V2** ★서버팀 요청 — PAUSE 전후 골 핸들 동일, `status` 가 CANCELED/FAILED 로 **안 바뀜**
- [ ] **V3** 그리퍼 개폐 중 → `DEFERRED_UNSAFE`, 완료 후 HELD (최악 11초)
- [ ] **V4** ★삽입 하강 중 → `STEP_BOUNDARY`, 지연 ≤1초, **벽이 그리퍼에서 안 밀릴 것**
- [ ] **V5** RESUME → 같은 골 유지, 중단된 phase 재시작 → `SUCCEEDED`
- [ ] **V5b** 벽 든 채 하강 중간 RESUME → 정렬 높이 복귀 → **재측정** → 하강
- [ ] **V6** ACK `stop_mode` ↔ `hold.stop_mode` 일치

> ⚠ **V4 가 이 중 유일하게 물리적으로 위험합니다.** 삽입 중 정지에서 벽이 죠에서 밀리면
> 그 뒤 하강이 기둥을 밀어냅니다. 첫 시도는 **벽 없이 빈 손으로** 동작만 보고,
> 그 다음에 벽을 물려서 하는 것을 권합니다.
>
> V1~V6 이 전부 통과하기 전까지 **`immediate_pause_enabled` 는 `false` 로 둡니다.**
> 그동안 실기는 v0.2 동작(phase 경계 정지)이고, ACK 는 `AT_PHASE_BOUNDARY` 로 사실대로 나갑니다.
