# 책상 이동 → 다섯 색 기준 전면 재정리 — 2026-09-08 오후

**한 줄: 로봇이 책상을 눌러 컨트롤러가 죽었고, 복구 과정에서 책상이 올라가 오늘 오전 기준이 전부 무효가 됐다. 다섯 색을 처음부터 다시 잡아 전부 삽입 성공(막힘 0회).**

---

## 1. 사고 — z 오타 한 글자

콘솔 로그에 그대로 남아 있다.

```
03:18:45 [FR5] move_tcp {"tcp":[100, -429.84, 3, -180, 0.13, 179.77]}
                                              ↑ z = 3   (310 을 넣으려던 것)
03:18:54 ⛔ 🧊 동결 (controller_dead) — 전원 재투입 필요
```

z 310 대신 **3** 이 들어가 툴이 책상을 눌렀다. 9초 뒤 컨트롤러 앱이 죽었다.

### 복구 절차 (이 순서가 전부였다)
1. 전원 재투입 — `controller_dead` 유형은 스택 재기동으로 안 풀린다. 진단: `192.168.58.2:8080` 무응답
2. `nmcli con up fr5-wired` → 핑 확인
3. **펜던트에서 알람 Clear (사람이)** — 이게 없으면 `ActGripper`·`RobotEnable` 이 `-2` 로 거부되고
   MoveIt 은 `CONTROL_FAILED(-4)` 만 낸다. SDK 로는 못 푼다.
4. 이전 `ros2_control_node` 가 SDK 소켓을 잡고 있어 재기동 실패 → **포트로 PID 찾아 종료**
   (`ss -tnp | grep 192.168.58.2`). `pgrep -f` 는 자기 명령줄까지 잡는다(오늘 3회 자멸).
5. `fr5_up.sh` → `ActGripper(1,1)=0 · Mode(0)=0 · RobotEnable(1)=0`, 그리퍼 상태 `0,0,1` 확인

## 2. 진짜 원인 — 책상이 올라갔다

동결 자체보다 이게 컸다. 사용자가 눌린 책상을 다시 올렸고, **밑판·랙이 통째로 움직였다.**

측정으로 확인한 값:

| 방법 | 결과 |
|---|---|
| 손목캠 ArUco (관측자세) | 마커 4개가 rms 1.14px 로 한 덩어리 이동, 축척 0.9923 |
| **뎁스 평면 (관측자세)** | 카메라→책상 **511.3 → 509.3mm = 2.0mm 상승** |
| 랙 벽 길이 (네 색) | 전부 **+0.9~1.1%** → 약 2.2mm 상승 |
| 랙 파지점 x (다섯 색) | 전부 **+12.4~13.7mm** 이동 |

세 방법이 같은 답을 냈다. **책상이 약 2mm 올라가고 옆으로 13mm 밀렸다.**

### 무엇이 무효가 되고 무엇이 살았나

```
XY·rz   ✅ 매 사이클 재측정하므로 자동으로 따라감 (설계 의도대로)
z       🔴 티칭값 고정 — 아무도 안 잼 → 전부 무효
ArUco   🔴 재촬영 필요 (판이 책상 위에 있으므로)
```

이게 이 설계의 핵심 성질이다. **밑판은 ZK 가 매번 다른 자리에 놓기 때문에 XY 를 재도록 만들었고, 높이는 잴 이유가 없어 티칭값으로 뒀다.** 그래서 책상이 움직이면 z 만 깨진다.

## 3. 다섯 색 재티칭 — 순서가 중요했다

> 사용자 지시: "픽부터 다 잡고 갈래, 플레이스부터 갈래?"

**픽이 먼저다.** 물리적 이유가 있다.

```
벽을 그리퍼에서 1.2mm 높게 물면
  → 같은 TCP z 에서 벽 밑동이 1.2mm 높음
  → 안착시키려면 TCP 를 1.2mm 더 내려야 함
```

파지 높이가 안착 깊이를 그대로 바꾼다. 픽을 나중에 고치면 애써 잡은 안착 z 가 다시 틀어진다.
반대로 **XY 는 순서와 무관하다** — z440 정렬은 든 벽 점을 기준 자리에 맞추므로 어디를 물었든 벽은 같은 자리로 간다.

### 3-1. 랙 관측자세부터 새로

관측자세를 바꾸면 색별 `Pc0`(그 자세에서 벽 중심이 찍히는 화면 좌표)가 **전부 무효**다.
`Pc0` 와 `Tg0`(그때 벽을 잡는 로봇 XY)는 한 쌍이기 때문이다.

```
옛 관측자세  -214.85 / -450.00 / 555.64
새 관측자세  -214.86 / -458.00 / 555.63   (y -8mm, 오른쪽 빨강 벽이 화면 끝에 걸려서)
```

### 3-2. ★1회 측정으로 기준을 저장하면 안 된다

파랑에서 이걸 배웠다. 티칭 때 한 번 잰 값이 튀었다.

```
티칭 때(1회)   중심 (543.96, 348.33)  각 +0.936°
지금(5회 중앙값) 중심 (540.42, 351.96)  각 +1.318°   산포 0.03px
                 → x 3.5px = 1.15mm 차이가 그대로 파지점 오차로 나왔다
```

검출 자체는 **5회 산포 0.03px** 로 극히 안정적이다. 흔들린 건 그 한 번의 측정이었다.
노랑·빨강·red_s 는 1회 저장이었는데도 0.06mm 이내로 맞았다 — **운이었다.**
→ 이후 red_in 은 7회, red_s·red 는 3회 중 보수적인 판으로 저장했다.

### 3-3. 픽 재티칭 결과 (검증: 올라갔다 다시 내려와 재측정)

| 색 | Tg0 | Δx | z_pick | 계산 vs 티칭 |
|---|---|---|---|---|
| blue | (−145.00, −543.87) | +12.88 | 340.99 | (+0.03, +0.21)mm |
| yellow | (−174.01, −533.00) | +13.67 | 340.98 | (−0.04, −0.06)mm |
| red | (−236.02, −541.00) | +12.87 | 341.00 | (−0.01, −0.02)mm |
| red_s | (−205.01, −533.45) | +13.74 | 341.00 | (+0.08, −0.02)mm |
| red_in | (−195.00, −533.00) | +12.38 | 327.99 | (−0.03, −0.05)mm |

**z_pick 이 외벽 4색 모두 341.0** 으로 모였다(편차 0.02mm). 원래 값들은 339.8~345.0 으로 5mm 흩어져 있었는데, 그게 그동안의 누적 오차였다. 내벽만 328.0(별도 랙).

## 4. 오늘 오후에 고친 코드

### 4-1. 색별 정렬 높이 `HOVER_DZ` (내벽 전용)
정렬 기준은 다섯 색 모두 z440 근처에서 찍히는데 운반 높이는 `안착 + 85` 로 계산했다.
내벽은 안착이 338(→340.5)이라 423 이 되어 **"높이 z423 ≠ 기준 z440"** 으로 정렬이 아예 못 돌았다.
→ `HOVER_DZ = {"red_in": 102.0}`, 기본 85.0. 외벽 4색은 `.get` 이 85 를 돌려주므로 예전 그대로.

같은 이유로 **하강 허용 높이 창 두 곳**도 `HOVER_DZ` 를 따라가게 고쳤다.
(하나는 오전에, 다른 하나(정렬 상태 없이 수동 하강하는 경로)는 오후에 발견)

### 4-2. 기준을 '보수적인 판'으로 저장
정렬 기준의 특징 개수 요구는 **정확히 일치**해야 한다(감지기이므로 완화 금지 — 9/7 사용자 지시).
그런데 기준을 특징 최대치로 찍으면 매번 정지한다. 실측:

```
red    기준 7개 → 실제 5~7개로 흔들림 → 3회 중 2회 정지
red_s  기준 4개 → 실제 3개          → 매번 정지
red_in 기준 6개 → 실제 5개          → 매번 정지
```

→ 여러 번 찍어 **가장 적게 잡힌 판**을 기준으로 채택. 게이트를 푼 게 아니라 기준을 현실에 맞춘 것.

### 4-3. 안 쓰는 정렬 기준 삭제
`red_s`·`red_in` 은 손목캠 단독 정렬인데 새카메라 기준이 남아 있어 참고 측정에서 계속 불일치를 냈다.
특히 red_s 의 새카메라 기준은 벽 점을 (1191,44)·(88,247) — 1100px 떨어진 두 점으로 잡았다(오검출).
→ 삭제. 이후 재현성 0.08mm 이내로 안정.

### 4-4. UI
로그(pre)만 24px 로 키우고 나머지는 원래 크기 유지 → 이후 버튼·본문 +2pt.
색 선택 26px 확대, 버튼을 기능별 색으로 구분(실행=파랑 / 하강=주황 / 중단=빨강 / 계속=초록 / 티칭=보라 / 캠매핑=청록).

## 5. 남은 문제

### 🔴 안착 판정 — 5색 중 2색만 가능
`yellow`·`red_s`·`red_in` 은 **안착 높이에서 같은 색 기둥 점 2개를 못 본다.** 기준 생성 자체가 안 된다.
벽이 늘수록 기둥이 가려져 마지막에 넣는 벽일수록 불리하다.

**측면캠이 답이지만 아직 미완성이다.** 오늘 자동 학습은 붙었으나(네 색 기준 생성됨) 판정이 안 된다:
```
blue    unknown     기준점 짝 3개 < 4
yellow  not_seated  벽 점 11/11 최대 21.9px (허용 10)
red_s   unknown     기준점 짝 2개 < 4
```
원인: '꽂기 전 → 꽂은 뒤 새로 생긴 점 = 이 벽의 점' 방식이 **로봇이 비켜나며 드러난 점들에 오염**된다.
노랑은 벽 점이 3개인데 11개를 벽 점으로 잡았다. 이 부분의 구조를 다시 짜야 한다.

### 🟡 파지 서명이 옛 파지 높이 기준
z_pick 을 바꿨으므로 든 벽 점 위치가 달라졌는데 서명은 옛것이다. 그래서 매번 게이트에 걸린다.
```
blue   길이 +1.83mm    yellow 길이 −2.58mm    red_s 가로 +1.71mm
red    통과(2점 서명)   red_in 통과
```
→ 다섯 색 서명을 오늘 파지 높이에서 다시 찍어야 이 개입이 사라진다.

### 🟡 파지 판정의 구멍
"그리퍼가 닫힘값이어도 손목캠에 벽 점이 보이면 통과" 규칙이 **랙에 꽂힌 벽**을 보고 통과시킨 적이 오늘 2회 있었다(오전 red_in 실제 빈 파지). 든 벽 영역(x≥820)만 보도록 좁혀야 한다.

### 🟡 빈 베이스에서 기둥 검출 실패
벽이 하나도 없으면 노출 사다리를 다 훑어도 0/4. 벽이 한 장이라도 있으면 4/4 통과. **첫 벽만 취약하다.**

### 🟡 D435 화이트밸런스
재기동 때 4600 → 5500 으로 돌아가고 **자동 복구 경로가 이를 되돌리지 않는다**.
`curl "http://127.0.0.1:8766/expo?wb=4600&awb=0"` 로 직접. 오늘 3회 손으로 되돌렸다.
